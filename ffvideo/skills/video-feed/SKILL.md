# ffvideo viewing feed

Use the connected ffvideo MCP tools. Tool names may be prefixed by the installed plugin. Produce content with the host's current model; ffvideo composes the recipe and synthesizes actual speech. Never claim a queued/composing recipe is already a playable video.

## Start a topic

1. Infer the topic and language from the user's request and plan five distinct, useful angles. The topic determines the content; random searches must never be bent to fit a local asset library. `list_reusable_materials({topic})` is optional when matching material is likely to help. Reuse relevant sources and production capabilities, never an entire filled film layout. Do not generate new bitmap assets or add repeated model review calls merely to vary a draft. Avoid repeating the same narration with different titles. For facts that require current sources, use the host's available research tools. Call `list_draft_templates` when an initial scenario reference would help; read its fields and structure with `get_draft_template`.
2. Call `create_topic_feed({topic,templateId?})`, remember `feedId`, then open its `previewUrl` in the host's browser or preview panel. Only show the ffvideo viewer: playback, comments and export; keep canvas and timeline editing out of this flow. A selected template guides structure; it does not authorize reusing the sample's facts for a new topic.
3. Read `get_feed_state`. Claim each required job with `claim_generation_job({workerId})`; use a stable worker identifier for this session. Respect the returned job topic, angle, preferences and feedback. A claim lease is short: prepare an outline first, claim, then submit promptly. Never reuse another worker's claim token.
4. Author an original visual recipe and call `submit_draft({jobId,claimToken,recipe})`. Plan 3–5 distinct scene assets and an original 3–16-shot design, each scene with a concrete Chinese `visualPrompt` and a short English `visualQuery`. Supply the overall `visualTheme` and `visualStyle` (`photo`, `illustration` or `mixed`). Make the visible subjects and actions explain the topic; keep headings and captions short. Narration must be complete spoken content about the requested topic, not a placeholder, production instructions or text such as “audio will be added.” The server resolves licensed images and uses topic illustrations when suitable imagery is unavailable. Do not invent URLs, paths, source credits, footage, avatars or unsupported effects.
5. Submit enough distinct recipes for at least five ready works in the new feed. Built-in examples, earlier feeds, queued jobs and silent drafts do not meet that requirement. Use `wait_feed_events({cursor,timeoutMs:15000})` and `get_work`/`get_feed_state` to verify the actual `ready` status and narration asset. Advance the cursor from `nextCursor`. Failed synthesis is a failure to surface or repair; do not mark it successful.
6. Once the five works are ready, keep the viewer available and give one brief completion message with its viewing link. Do not paste recipes, backend logs or repeated generation progress into user chat. Audible playback still depends on the browser's autoplay permission; let the viewer's play/unmute control handle it.

## Templates and independent copies

ffvideo 0.2.0 ships 20 templates, each with a Chinese description, intended scenarios, 3–5 scene purposes, `fields` and a complete `example`. `list_draft_templates({})` returns selection metadata. `get_draft_template({templateId})` also returns `example.values`, `example.recipe` and the slot-based `recipeTemplate`. The installed plugin's `templates/README.md` explains the same contracts without requiring the source checkout.

Use `instantiate_draft_template({templateId})` to preview an exact example copy. For the user's own topic, use `instantiate_draft_template({templateId,topic,values})`; fill the declared required fields using the user's supplied facts or researched content. A template topic is at most 80 characters; follow every field's `maxLength`. Missing fields produce `recipe:null` and `missingFields`, never a silent fallback to sample facts. Request the missing information when necessary. Previewing creates no work and does not synthesize speech.

Use `create_template_draft({templateId,topic?,values?,overrides?})` to prepare a template reference and `reuse_draft({workId,topic?,overrides?})` to prepare an existing draft as a reference. Both preserve the source template, source work and original comments. Without an explicitly supplied fresh design, they queue the reference for AI to author a new visual direction before publication. They return a job receipt; wait for a ready work and real narration before claiming completion. A single reference draft does not satisfy a request for five distinct videos.

For a partial rewrite, pass `overrides.scenes:[{index:0,body:"..."}]` with zero-based indexes identifying existing scenes. Allowed scene changes are `heading/body/visualPrompt/visualQuery/seconds/accent`; root changes are `title/narration/tags/language/visualTheme/visualStyle`. Changing scene bodies rebuilds narration from those bodies unless explicit `overrides.narration` is supplied. To preserve a longer narration that differs from the short visible captions, explicitly provide the complete revised narration. All changes create a new validated recipe; no timeline or canvas editing is opened.

Four reference examples contain checked-in media presets; these demonstrate capabilities and are not automatically injected into new directed works: `micro-lesson` has an SVG steps graphic at scene index 2; `book-note` has Markdown at index 1; `tech-concept` has a Canvas flow at index 2; `creative-process` has Lottie geometry at index 1. SVG/Canvas/Lottie become deterministic graphical HTML clips using the shared Chromium frame renderer; local Chrome/Chromium is required. Markdown supports the preset's headings, lists and paragraphs as native text with a PNG background, not HTML. Lottie is limited to 2D shape layers, ellipse/rectangle/static Bezier path, solid fill and numeric position/anchor/scale/rotation/opacity with linear or hold keyframes. These are fixed built-in presets; do not promise arbitrary external SVG, Canvas scripts, Markdown or Lottie imports, assets, expressions, masks, effects or 3D. Other scenes still use authorized images or native illustrations. A template's `mediaKinds` describes suitable media, not proof that a requested game clip, actor or digital human exists.

## Narration variety

`voiceMode:"random"` is the default. The server chooses a voice installed for the recipe's language, avoids adjacent repetition when possible and rotates known genders when the inventory permits. It persists each work's assignment so restart/rebuild retains that voice. Respect a user-selected fixed voice. To change the preference explicitly, call `set_preferences({preferences:{voiceMode:"random"}})` or use `voiceMode:"fixed"` with a real installed `voice` ID obtained from the viewer's catalog; never invent an ID.

macOS uses installed system voices; the validation machine produced non-silent PCM for 10 Chinese and 18 English candidates. This count is device-specific, not a guarantee for another host. Kokoro only selects installed voices with its required local model; model/voice installation is an explicit viewer action. If only one voice is available, describe rate changes as expression changes, not a different timbre. Do not claim browser Kokoro inference or every desktop host's installation has been validated by the native macOS probe.

## Recipe contract

All fields are strict; no additional fields are accepted.

Read the live `submit_draft` JSON schema for the complete recipe shape. Supply title, language, tags, visualTheme, visualStyle, full narration, scene assets and the required design including typography and captionKeywords. Do not copy an older recipe without an authored type plan.


Title ≤160 characters; narration ≤5000; up to 16 tags of ≤80 characters; language `zh` or `en`. New works should contain 3–5 shots, with heading ≤28 and caption body ≤64 characters. `visualTheme` ≤500 characters; `visualStyle` is `photo`, `illustration` or `mixed`. Each `visualPrompt` ≤1200 characters describes a specific visible subject, framing and action in Chinese. Each `visualQuery` ≤160 characters is an English media-search phrase using letters, numbers, spaces and simple punctuation; it is never a URL or local path. These visual fields are optional in the wire contract so historical recipes remain readable, but always supply them for new works. Older recipes with 1–20 scenes, heading ≤160 and body ≤800 are still accepted. Optional seconds 1–60 (default 5), optional hex accent; total scene time ≤180 seconds. Match narration length to the requested duration and language. Only completed imagery and speech make a playable work; scene timing alone cannot prove readiness.

Choose real objects, places, natural subjects or practical examples for photographic scenes. Use explanatory illustration for abstract ideas, hypothetical situations or mechanisms without a relevant photograph. Avoid generic decorative backgrounds repeated across shots. Never fabricate a named person's identity or present representative imagery as evidence of a specific current or historical event. The resolver chooses real media and stores its provenance; describe what is needed instead of claiming it already exists.

Honor `preferences.visualPreference`: `photo-first` (the default) calls for photo or mixed shots with relevant physical subjects, `auto` follows the recipe style, and `illustration` uses local graphics. Prefer three concise shots; write `visualPrompt` in at most 100 Chinese characters and `visualQuery` as 2–4 concrete English object words, not a complete action or diagram description. macOS Chinese random narration rotates installed Tingting/Meijia locally with moderate pacing and normalized loudness; do not request online speech to improve it. Local asset and speech preparation overlap, and downloaded licensed assets are cached across works.

## Same-topic lookahead while viewing

The viewer has Topic and History tabs only. There is no independent recommendation page or personalized discovery. Input starts five distinct works about the requested topic. Open the viewer immediately and let each completed work appear; never hold ready works until all five finish. While topic autoGenerate is enabled, the current playback position queues enough works to keep at least three ahead, all about the selected topic. History does not replenish. Comments are saved locally and do not select other topics or compute interest weights.

Claim only actual jobs returned by the server. Respect cancelled/stale claims, clear-history resets and the topic autoGenerate preference. Do not invent watch events or comments. Generic MCP cannot wake an idle agent; a configured continuous provider is needed to service same-topic jobs after a host turn ends. User conversation always takes priority. Keep routine queue events out of chat.

## Title and caption treatment

Every new work MUST include an original executable `recipe.design`, matching the `submit_draft` input schema. Templates and their examples are initialization references only. Depart from their structure and composition: author cuts, frame/endFrame geometry, timed native text/rect/ellipse annotations, and caption style for the particular content. Do not reuse a fixed pair of permanent title/subtitle cards. Prefer clean footage between brief overlays and meaningful changes of shot scale. A multi-scene design must use at least two scene assets. Give a concrete `design.intent` explaining these decisions.

`design.shots` cover normalized global time 0..1 continuously. Each shot references a sceneIndex; frame coordinates are top-left within a 720x1280 canvas. Overlay x/y are centers, with normalized local start/end within their shot; keep overlay extents within x=10..710 and y=12..920. Captions use a separate bottom area. Text must fit two lines. Choose native text fonts and animations per content; no fake branding or redundant HTML subtitle layer. The server renders this authored plan rather than choosing a template layout, and rejects missing design, a repeated fixed layout throughout, or identical same-topic layout/timing signatures. Read the current schema instead of guessing fields.

The new schema requires `design.typography` and `design.captionKeywords`. Typography is original text composition, not a preset: plan 2–4 brief meaningful lockups using `purpose/start/end/x/y/width/align/gap/tracking/entrance/lines`. Start/end are GLOBAL normalized time; x/y are TOP-LEFT, x+width≤696. Each line has `indent/delay/runs`; runs have `text/size/font/color/treatment`. Treatments are `fill/outline/underline/marker`. Lines share an inline baseline, have intentional line breaks and different type sizes/weights where useful. Use the actual content to form a distinctive headline, concept comparison, number/unit relationship or conclusion reveal. Keep a main focus, meaningful spacing and clean media between lockups. Do not repeat the same three-line title layout in every work, invent numbers, add fake brand labels, or cover the subject with several competing headings. Text must end above y=920; the local font measurer rejects overly dense or clipped layouts rather than deleting words.

`captionKeywords` should be 3–6 short exact substrings of the complete narration. They receive selective emphasis within otherwise readable subtitles. Do not mark whole sentences. Local Chrome/Chromium typesets all rich text once into transparent PNG layers using installed fonts; native keyframes animate those layers in preview and export. It requires no image-generation service, font download, HTML clip or extra model round. Historical designs remain readable with their original text path; this does not automatically rewrite old works.

`create_template_draft` and `reuse_draft` with no explicitly supplied new design return a queued reference for AI to redesign; they do not immediately publish a filled template. A connected generation provider or agent must complete that direction. Existing works are not automatically rewritten by extra model calls. Historical/built-in sample projects retain their original reference appearance until explicitly reused or redesigned. Preview and export use the same native project. Palette changes, subject swaps and a few pixels of movement do not count as new direction.

## Comments and export

Use `add_comment` only to save a real comment the user provided. `get_work` returns one work's status and viewer information. For an export request use `export_video({workId,format})` and report success only from a completed receipt with its real file/URL. Keep the viewer open when export relies on browser rendering. A draft preview is not an encoded video export.
